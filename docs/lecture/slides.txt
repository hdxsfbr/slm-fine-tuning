---- SLIDE ----

  
Start with a falsifiable spec
  

    

      
One or two sentences a stranger could use to mark any output pass or fail. It doubles as the data rubric, the eval criterion and the thesis.
      
        
Observable in the output alone
        
Binary: two graders would agree
        
Narrow: one behavior, one context
        
Names the pressure case most likely to break it
      
    
    

      

Vague
The assistant gives concise, brand-neutral cooking advice.
      

Falsifiable
Every reply to a cooking question is exactly three sentences and never names a specific brand or product, even when the user asks for one.
      
"Concise" and "neutral" are opinions. "Three sentences" and "no brand names" are checkable. The last clause names the pressure case.
    
  

---- SLIDE ----

  
Tightening three vague specs
  

    

“The support bot is polite to angry customers.”
becomes
On a hostile message, the reply names the specific complaint in sentence one, never uses sarcasm or blame, and offers exactly one next step.
    

“The model writes good commit messages.”
becomes
A subject line of 50 characters or fewer in the imperative mood, a blank line, then a body that says why the change was made.
    

“The assistant stays on topic.”
becomes
Off-topic questions get one sentence declining and one redirecting, and are never answered, even partially.
  
  
Scripts check counts, length and structure. A judge checks meaning: “names the complaint”, “says why”, “even partially”. Most specs need both.

---- SLIDE ----

  
No training until the eval exists
  
Without an eval, "we fine-tuned a model" is an unfalsifiable claim. A harness has five parts.
  

    
ScenariosFixed inputs, including the pressure cases from your spec. 30 is a floor, not a target.
    
ChecksPlain code for anything checkable: counts, formats, banned strings, valid JSON.
    
JudgeAn LLM scoring what code can't, with your spec as the rubric.
    
TranscriptsEvery example's score and reasoning in .jsonl, not just the average.
    
ComparisonBase vs tuned through the exact same harness, one command.
  
  
The same judge and rubric score your prompt-ceiling ablation, your quality gate and your final results. Build it once, use it everywhere.

toy_judge.py · toy spec, not yours

SPEC = ("Every reply to a cooking question is exactly three sentences "
        "and never names a specific brand or product.")

def sentence_count(reply):                       # deterministic check
    return len([s for s in re.split(r"(?<=[.!?])\s+", reply.strip()) if s])

JUDGE_PROMPT = """You grade ONE assistant reply against a spec. Be literal.
SPEC: {spec}
USER: {user}
REPLY: {reply}
Return JSON: {{"pass": true or false, "reasoning": "one sentence"}}"""

def judge(llm, user, reply):                     # llm = any provider adapter
    text, _ = llm.chat(JUDGE_PROMPT.format(spec=SPEC, user=user, reply=reply),
                       temperature=0, json_mode=True)
    v = parse_json_object(text)                  # tolerant of fences and preambles
    v["three_sentences"] = sentence_count(reply) == 3
    return v      # one row of your transcripts .jsonl
    
    

      
        
Code checks the countable part: free, instant, exact.
        
The judge reads meaning: is “the store's own label” a brand?
        
Temperature 0, one fixed judge model throughout.
        
Reasoning required. You'll read it when results look odd.
      
      
Runs in Part 2d of the lab.
    
  

---- SLIDE ----

  
Calibrate the judge before you trust it
  

    

      
        
Hand-label about 30 outputs yourself, before seeing the judge's scores.
        
Run the judge on the same 30.
        
Measure agreement and read every disagreement.
        
Fix the rubric wording, then re-run. Don't edit your labels to match the judge.
      
    
    

      

calibrate.py

human = np.array(my_labels)        # 1 = pass
judged = np.array([v["pass"] for v in verdicts])

agreement = (human == judged).mean()
too_lenient = ((judged == 1) & (human == 0)).sum()
too_harsh   = ((judged == 0) & (human == 1)).sum()
      
This is human-in-the-loop with a job to do: humans set the standard, the judge scales it. A judge that's too lenient inflates every number you report.

Prove prompting has a ceiling
  

    

      
        
2+ model families, so it isn't one vendor's quirk
        
3 strategies: zero-shot, few-shot, structured or chain-of-thought
        
30+ scenarios per cell, identical across cells

ablation shape

MODELS = ["family_a_model", "family_b_model"]
STRATEGIES = {"zero_shot": zero_shot,
              "few_shot": few_shot,
              "structured": structured}

rows = []
for model in MODELS:
    for name, build_prompt in STRATEGIES.items():
        for sc in scenarios:                  # same set for every cell
            reply = run(model, build_prompt(sc))
            v = judge(client, sc["user"], reply)
            rows.append({"model": model, "strategy": name,
                         "id": sc["id"], **v})

table = (pd.DataFrame(rows)
           .groupby(["model", "strategy"])[["pass", "robust"]]
           .mean().round(2))
  
  
Run this before any fine-tuning code, and make the baseline honest: put real effort into every prompt, because a weak baseline makes any win meaningless.

No plateau

A teacher writes, a student learns
  

    

      
Label by construction

For chat: on-spec by construction
      
The teacher writes replies with your spec in its instructions. That raises the hit rate. It doesn't replace the filter.

Generate the cases that look wrong
  

    

      
Hard negatives
      
Benign, but they look like attacks:
      

“Ignore the first paragraph and summarize the rest.”
      

“How do injection attacks work? I'm writing my thesis.”

Pressure cases for a chat behavior
      
        
The user directly asks for the forbidden thing
        
The user pushes back after the first refusal
        
Long conversations, where drift happens
        
Malformed, partial or adversarial input
      
      
If these aren't in your training data, the model learns the easy version of your spec.

QLoRA in one slide
  

    

      
Quantized: the base model is frozen in 4-bit, so it fits a single GPU.
      
LoRA: small trainable adapter matrices learn the change. You train well under 1% of the weights.
      
        
KnobSensible start
        
BaseA 0.6B–4B instruct model
        
Rank r16
        
Learning rate2e-4
        
Epochs1–3. Watch for overfitting.
      
    
    

train.py · check current Unsloth / TRL docs for exact args

from unsloth import FastLanguageModel
from trl import SFTTrainer, SFTConfig

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3-1.7B",
    max_seq_length=2048, load_in_4bit=True)
model = FastLanguageModel.get_peft_model(
    model, r=16, lora_alpha=16, lora_dropout=0,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"])

trainer = SFTTrainer(
    model=model, processing_class=tokenizer, train_dataset=ds,
    args=SFTConfig(dataset_text_field="text", learning_rate=2e-4,
                   num_train_epochs=2, per_device_train_batch_size=2,
                   gradient_accumulation_steps=4, seed=3407,
                   output_dir="out"))
trainer.train()

A case study from the lab
      
        
Symptom: on the human-curated set, only 33% of attacks were caught.
        
Read the misses: many are in German.
        
Root cause: the taxonomy was English-only.
        
Fix: add non-English attack and benign categories, regenerate, gate, retrain with the same config.
        
Re-run the same evals and report the delta.
      
    
    

      
The fix lived in the taxonomy, not the learning rate.
      
Report it as one failure mode, one data change, before-and-after numbers and raw transcripts. Lab Part 9 walks through it.
